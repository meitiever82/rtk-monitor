# rtk-monitor 设计文档

日期：2026-08-31
状态：已与需求方逐节评审通过，待终审

## 1. 背景与目标

踏歌矿区车辆的 RTK 定位持续出现问题，但车端 CGI-610 组合导航仪只输出融合后的结果（CAN），
无法定位故障发生在链路的哪一级（基站 → 平台 5G 广播 → 板卡 RTK 解算 → 惯导融合 → 下游软件）。
2026-08-27 的 58 分钟 CAN 录包分析表明该时段设备全程 RTK 固定解、状态健康，
说明故障要么未被录到，要么发生在设备自报状态无法反映的环节（如基站坐标变动）。

本项目交付一个**车载 RTK 定位监控诊断 APP**（9 月交付），常驻车载电脑，
接入定位链路各级数据，独立解算、实时展示、自动诊断、落盘记录，回答两个问题：

1. 此刻定位是否可信？不可信的原因是什么？
2. 历史上出问题的时刻，故障发生在链路的哪一级？

### 1.1 已确认的需求决策

| 决策项 | 结论 |
|---|---|
| 运行形态 | 车载电脑上的服务 + Web 界面（浏览器访问，本机或远程） |
| 解算深度 | 内嵌 RTKLIB（demo5 分支 rtkrcv）独立解算 RTK |
| 地图底图 | 离线卫星影像瓦片（MBTiles + Leaflet） |
| 数据接入 | 四路全接：差分 RTCM、板卡原始观测、纯卫导解、CAN 融合输出 |
| 部署硬件 | ARM64（Orin / RK3588 等），Docker 部署 |
| 分析功能 | 四路裸流落盘 + 历史回放 + 事件自动标记与报告 |
| 与 GLIM 的关系 | 独立进程，不嵌入 GLIM；对外发布解析后数据，GLIM 二期经适配器订阅 |
| 界面语言/主题 | 中文，深色为主 |

### 1.2 外部环境（现场事实）

- 差分链路：踏歌自建**单基站** → 平台服务器 → 5G 无线网向车端广播（协议待确认，见 §11）。
  非 VRS，改正数对所有车相同，任意客户端连平台广播端口即得等价流。
- CGI-610 数据输出（手册已确认）：
  - TCP Server7 / TCP-UDP Client7 可输出"GNSS 板卡数据（原始观测）、卫导数据（未融合解）、
    组合数据、IMU 原始数据（最高 100 Hz）"，网页 I/O 设置中勾选；
  - CAN 口输出 50 Hz 融合结果（现有 decode_cgi610.py 已完成解码，字节序为小端）；
  - 差分接入走设备 RTK 客户端（TCP）或串口 C 输入。
- 矿区特有故障模式：坑底/高帮处卫星遮挡与 5G 盲区叠加；单基站坐标变动会导致
  全矿车辆在"保持固定解"状态下整体平移。

## 2. 总体架构

单个 ARM64 Docker 容器（host 网络模式，需访问 SocketCAN），容器内两个进程：

```
┌─ 容器 ────────────────────────────────────────────────┐
│  主进程 (Python 3.11+ / asyncio)                       │
│  ├─ 采集协程 ×4（差分TCP、原始观测TCP、卫导解TCP、CAN）    │
│  ├─ 本地转发端口 ×2 ──→  rtkrcv 子进程 (RTKLIB demo5)    │
│  ├─ 解析层（RTCM 帧切分 / GPCHC / CAN 解码）              │
│  ├─ 诊断引擎（规则链 + 事件状态机）                        │
│  ├─ FastAPI + WebSocket ←─ rtkrcv solution/status 回读  │
│  └─ 存储层（裸流滚动落盘 + SQLite 历元/事件表）            │
└───────────────────────────────────────────────────────┘
      浏览器（车上/远程）访问 http://<车IP>:8080
```

设计原则：

- **采集永不停**：采集协程只做"收 → 落盘 → 入队"三件事；解析、解算、诊断、界面中
  任何一环异常都不影响原始数据落盘。诊断工具自身必须比被诊断对象可靠。
- **rtkrcv 是子进程不是库**：通过本地 TCP 喂入数据、读取其输出；进程退出即自动重启；
  RTKLIB 代码零改动，升级 demo5 版本不影响本项目代码。
- **实时与回放同构**：回放走与实时完全相同的 WebSocket 消息格式，前端不区分数据来源。
- 容器 `restart: always` 兜底，开机自启。

### 2.1 模块划分

| 模块 | 职责 | 依赖 |
|---|---|---|
| collector | 四路数据接入、断线重连（指数退避）、裸流落盘、入队 | 无（最底层） |
| parser | RTCM 帧切分与消息号提取、GPCHC/HCINSPVATZCB 解析、CAN 解码 | collector 队列 |
| solver | rtkrcv 生命周期管理、本地转发端口、solution/status 解析 | collector 队列 |
| diagnosis | 规则链评估、事件状态机、结论生成 | parser、solver 输出 |
| store | SQLite 读写（历元表、事件表）、裸流文件索引、磁盘清理 | parser、diagnosis |
| api | FastAPI：WebSocket 实时推送、回放控制、报告生成、静态文件托管 | store、diagnosis |
| publisher | UDP JSON Lines 对外发布（gnss_fix / gnss_event） | diagnosis |
| web | 前端单页应用（Vue3 + Leaflet + uPlot） | api |

每个模块独立可测：collector 可对模拟 TCP 源测试；parser 对真实录包字节测试；
diagnosis 对构造的指标序列测试；前端对录制的 WebSocket 消息序列测试。

## 3. 数据接入与落盘

### 3.1 四路数据

| 路 | 来源 | 接入方式 | 落盘格式 |
|---|---|---|---|
| 1 差分 RTCM | 平台广播端口 | TCP client | 裸流按小时分文件 + sidecar 索引 |
| 2 板卡原始观测 | 610 TCP Server7（仅勾"GNSS 板卡数据"） | TCP client | 同上 |
| 3 纯卫导解 | 610 TCP/UDP Client7（勾"卫导数据"，GPCHC/HCINSPVATZCB） | TCP server（收 Client7 回传）或 TCP client，依 610 配置定 | 裸流 + 解析入 SQLite |
| 4 CAN 融合输出 | SocketCAN（can0） | python-can | candump 兼容文本（与现有 record_can.sh 一致）+ 解析入 SQLite |

sidecar 索引为 JSON Lines，每条消息一行：`{t, type, off, len}`（分别对应主机时间、
消息类型、裸流内字节偏移、消息长度），用于主机时间与流内 GPS 时间的对齐及按时间段
快速定位字节区间。

### 3.2 落盘与清理

- 目录按天：`/data/gnsslog/YYYYMMDD/`，文件按小时：`corr_20260901_13.rtcm3` 等；
- 裸流原样存储不加壳，保证可直接输入 convbin / rnx2rtkp 离线复算；
- 后台清理任务双条件：保留天数超过 `retention_days` 或磁盘使用率超过 `disk_watermark`
  时从最旧日期起删除；两参数入 config.yaml；
- **断线即事件**：任何一路断开/恢复写入事件表（差分断流是一级诊断信号）。

### 3.3 rtkrcv 喂数

collector 将路 1、路 2 在 localhost 重新 serve（两个端口），rtkrcv 以 `tcpcli` 方式连接。
录制与解算解耦：rtkrcv 重启不中断落盘，落盘故障不影响解算。

## 4. 解算与诊断

### 4.1 rtkrcv 配置

- RTKLIB demo5 分支（rtklibexplorer 维护），kinematic 模式，GPS+BDS+GAL+GLO+QZS；
- 输入：rover = 路 2（RTCM3 MSM），base = 路 1（RTCM3），星历取自两流中的电文；
- 输出：solution 流（llh、Q、卫星数、σENU、差分龄期、ratio）+ solution status 流
  （逐卫星残差、SNR、高度角、方位角、周跳计数），均由 solver 模块以 1 Hz 汇总；
- 基站坐标：以路 1 中 1005/1006 电文为准（rtkrcv `-p` base position from RTCM）。

**独立性边界（重要）**：APP 与 610 共用同一根天线、馈线、板卡前端（路 2 来自 610 板卡）
与同一路差分改正数（路 1 来自平台广播）。"独立解算"独立的是**算法层**（610 板卡与
RTKLIB 是两套实现、两套参数），数据层不独立。按故障类型，能力边界如下：

- **观测噪声类**（多路径、坑底遮挡、周跳）：两套引擎取舍不同，偏差通常 ≠ 0；APP 可凭
  独立参数（elmask、SNR mask、模糊度策略）差异化处理，**可能优于 610**——这是自建解算
  的核心价值。
- **RF 前端/天线/馈线硬件故障**：观测信号整体劣化，两套引擎都无规律乱跳，偏差不为 0
  但**无法定位**（garbage in，调参不可救）。
- **基站坐标平移**：rover = base + 基线向量，base 坐标来自共享的 1005/1006 电文。base 错
  Δ 时，两套引擎各自正确解出的基线叠加同一个错 base，**同步平移 Δ、偏差 ≈ 0**。这是几何
  强制，与"谁抄谁"无关——两套独立实现错得一模一样，恰是"公共输入带偏"的指纹。此故障对
  独立解算**天然隐形**，必须依赖直接监控（§4.2 规则 2 的 1005 比对、绝对基准校验）。

### 4.2 诊断规则链

每秒对四路指标执行一次，按优先级取第一条命中的结论；无命中即"RTK 固定"。
阈值全部入 config.yaml（下表为默认值）。

| 优先级 | 规则 | 默认条件 | 结论模板 |
|---|---|---|---|
| 1 | 差分中断 | 路 1 无消息 > 3 s 或龄期 > 10 s | 差分中断 {n}s——5G 链路或平台转发问题 |
| 2 | 基站坐标变动 | 1005 坐标较基准偏移 > 0.1 m | ⚠ 基站坐标变动 {d}m——全矿定位将整体平移 |
| 3 | 卫星不足 | 共视卫星 < 6 | 卫星数不足（{n} 颗）——高帮/坑底遮挡 |
| 4 | 多路径 | ≥2 颗卫星伪距残差 > 2 m 且（高度角 < 20° 或 SNR < 35 dBHz） | {sats} 残差异常——疑似多路径 |
| 5 | 模糊度未固定 | Q=2 且 ratio < 3 | 模糊度无法固定（ratio={r}）——遮挡过渡区常见 |
| 6 | 周跳频发 | 周跳计数 > 5 次/30 s | 载波频繁失锁——动态遮挡或天线/馈线问题 |
| 7 | 610 离群 | 610 融合解与 APP 自解水平偏差 > 3σ 且持续 > 5 s | 610 输出与独立解算偏差 {d}m——疑似 610 融合问题 |

**诊断口径说明**：

- 规则 3"共视卫星"= 基站与 rover 共同观测的卫星数，由路 1 电文解出的基站卫星集与
  路 2 rover 卫星集取交集（rtkrcv solution status 中参与解算的卫星即共视子集）。
- 规则 4 阈值（残差 >2 m、高度角 <20°、SNR <35 dBHz）为初始默认，矿区低高度角卫星
  伪距残差偏大，需现场标定防误报。
- 规则 7 的 σ 取**最近 10 分钟 610-vs-自解差值的经验标准差**（排除当前偏差窗口），
  而非 610 自报 σ——否则"自信地错"（σ 小、位置错）的 610 不会触发。另 610 CAN 为
  50 Hz 融合解，INS 滤波有固有滞后（数十至百 ms 级），转弯/加速时表现为持续水平偏差、
  易误报，需实车标定并补偿融合时延，或对动态工况（加速度/角速度超阈值）下规则 7 加闸。
- 诊断节律为 1 Hz：<1 s 的瞬态故障（快速周跳、短 dropout）不可见，为本期分辨率上限。

基站坐标"基准值"：首次运行取连续 10 分钟 1005 中位数并持久化；此后偏移即告警，
人工确认后可在界面上一键更新基准（更新动作落事件表，含操作者与前后值；历史 1005
记录绑定当时基准版本，不追溯重解释）。

**规则 2 的覆盖盲区与兜底**：1005/1006 广播的是操作员**配置**的基站坐标，非物理真值。
若基站天线被碰、标石沉降而配置未更新，1005 仍播旧坐标，规则 2 不命中，但改正数已按
错误位置计算，全矿车辆在保持固定解状态下整体平移——此故障对规则 2 隐形。兜底手段为
**绝对基准校验**：坑内布设已知坐标的静态控制点（标石/已知坐标停靠位），车辆经过或停靠
时以 APP 自解与已知坐标比对，偏差超阈值（默认 0.2 m）告警"全矿整体平移嫌疑"。控制点
坐标入 config.yaml，校验结果落事件表。

### 4.3 事件状态机

规则命中产生 open 事件，条件恢复且持续 10 s（迟滞）后 close。事件记录
{类型、级别、起止时间、起止位置、峰值指标、结论文本}，入 SQLite 并实时推送前端。
同一历元**所有命中的规则及各自指标全部入事件**（含优先级较低者），不因"取第一条结论"
而丢弃——故障常复合（如基站变动与多路径叠加），保留完整信号供二期按场景切分用例。

## 5. 前端界面

中文、深色为主，Vue3 + Leaflet + uPlot，构建产物由 FastAPI 托管静态文件。

布局（桌面/车载横屏）：

- **状态条**（顶部常驻）：解状态大徽章（绿=固定/黄=浮点/红=单点·推算/灰=无数据）+
  非固定时的原因一句话；卫星数、龄期、σ、速度、GPS 时间；
- **地图区**（左主区）：离线影像瓦片；三条轨迹可独立开关——610 融合（主）、APP 自解、
  610 卫导；当前位置航向箭头 + σ 误差圈；**轨迹按解状态着色**（问题路段的空间规律
  在地图上直接可见）；
- **右栏**：天空图（卫星方位/高度角分布，颜色=SNR，标记被剔除卫星）+ 事件列表
  （点击跳转回放至事件前 30 s）；
- **时间线区**（底部）：卫星数、龄期、σ、ratio 四条曲线，共 x 轴联动缩放；
- WebSocket 推送：状态/指标 1 Hz，位置 5 Hz（5 Hz 位置来自 610 CAN 降采样；APP 自解
  为 1 Hz，轨迹按 1 Hz 呈现）；断连自动重连并显示"数据中断"横幅。

## 6. 回放与报告

- **回放**（展示回放）：界面选时间段 → 后端从 SQLite 按原时间轴重推（1×/10×/60×），
  消息格式与实时完全一致；历元表每秒存一份紧凑逐卫星摘要（卫星号/高度角/方位角/SNR/
  参与解算标志），约 15–20 MB/天，供天空图回放。
  注：本项目"回放"分三种形态，勿混淆——① 展示回放（本节，从 SQLite 重推已存指标）；
  ② CI 重放（§8 replay_sources.py，把录包按时间戳重放为 TCP/vcan 供测试）；③ 重算回放
  （把裸流重新喂入 rtkrcv/rnx2rtkp 用不同参数重解）。③ 本期不实现，是二期自优化切分
  用例与实验执行的基础，届时复用 ② 的重放内核。
- **报告**：按天或选定时间段生成 HTML（打印即 PDF）：固定解可用率（总体 + 分小时）、
  事件汇总表、问题路段地图标注、基站坐标稳定性曲线、610 与独立解偏差统计、
  绝对基准校验曲线（控制点比对）。绝对基准校验为必含项——基站物理平移时前述各项
  可能全绿，唯此项能暴露整体平移。

## 7. 对外发布接口（GLIM 二期）

APP 本体不依赖 ROS。UDP 单播/组播发布 JSON Lines，格式文档化、`ver` 字段版本化：

```json
{"type":"gnss_fix","ver":1,"gps_time":...,"host_time":...,"lat":...,"lon":...,"alt":...,
 "q":1,"sigma_e":0.01,"sigma_n":0.01,"sigma_u":0.03,"heading":...,"source":"rtkrcv"}
{"type":"gnss_event","ver":1,"gps_time":...,"host_time":...,"event":"corr_outage","state":"open","detail":"..."}
```

其中 `gps_time` 与 `host_time` 分别代表 GPS 时间和主机 Unix 秒：fix 消息中 `gps_time` 为 GPST（rtkrcv 解出的 GPS 时间），`host_time` 为该解抵达主机的时刻；event 消息中两者相等（都是诊断事件的触发时刻）。跨流对齐应使用 `host_time`。

需要 ROS 时另起可选薄适配器进程（UDP→topic），casbot/GLIM 扩展模块订阅适配器输出。
APP、适配器、GLIM 三者独立升级。

## 8. 测试策略

- **数据源模拟器**（tools/replay_sources.py）：把已录四路文件按原始时间戳重放为
  TCP 流 + vcan，支撑无真车的全链路端到端测试，同时是 CI 集成测试的驱动器；
- **单元测试**：三类解析器以真实录包字节为样本（2026-08-27 CAN 录包现成可用）；
  诊断规则以构造的指标序列断言结论（断流、基站跳变、遮挡等场景各一）；
- **解算链路**：先以 RTKLIB 自带样例数据验证 rtkrcv 集成；首批四路实录数据回来后
  固化为金标准用例（复算结果与当时记录的解逐历元比对）；
- TDD：每个模块先写测试再实现。

## 9. 部署

- 单 ARM64 镜像，multi-stage：编译 demo5 rtkrcv → 前端构建 → Python 运行层；
- docker compose：host 网络、`/data` 卷、`restart: always`；
- APP 自身可调项集中于 `config.yaml`：四路地址端口、CAN 口名、瓦片路径、诊断阈值、
  保留天数/磁盘水位、UDP 发布地址、Web 端口、控制点坐标。
- rtkrcv 解算参数独立于 `config.yaml`，存于其 `.conf` 文件（随镜像内置、运行时只读）。
  解算参数与诊断阈值分属两个配置域，各自独立、分别版本化（为二期参数空间 schema 铺路）。
